---
title: Sequence ranges
description: Give each node blocks of a sequence's values, so rows inserted on different nodes never share a key.
---

Nodes that all insert into the same table need keys that never collide. Sequence ranges give each node blocks of a sequence's values that no other node uses, with no change to the tables or the sequence's type. `nextval` and column defaults keep working as before.

## Enabling

On the node that will own the sequence's values, name every other node that issues values from it:

```sql
SELECT worf.enable_sequence_range('inventory_id_seq', participants := '{node_beta}');
```

The other nodes learn of the sequence over their subscriptions, so each node needs a subscription to or from another node in the topology. The user in each provider connection string needs `EXECUTE` on `worf.sequence_range_exchange`, which `PUBLIC` doesn't have. A provider tells the nodes that call it apart by these users alone, so give each subscriber node its own: a user that isn't a superuser speaks for the first node it calls for, and no other, until its row in `worf.sequence_range_role` is deleted. A node re-created under a new name, with the same subscription name and user, takes over its old node's slot then, or, for a superuser, once the old node has been silent for three exchange intervals and a timeout. Once every participant has reported, the owner starts granting blocks above every value any node has issued or stored. Until a node gets its first block, and whenever it has none, as while a reset owner is fenced, its `nextval` fails with SQLSTATE `2200H`, "reached maximum value" (or minimum, for a descending sequence) at the edge of the sequence's type where worf parks it, such as -9223372036854775807; `worf.sequence_ranges` shows why. A node that joins later, with values that already reach into the granted range, is refused: its state shows `refused` and its `nextval` keeps failing.

```sql
SELECT * FROM worf.sequence_ranges;
```

shows each sequence's state, its active and next blocks, and the values left. `worf.sequence_range_grants` lists the blocks this node granted. A role that isn't a superuser needs `USAGE` on schema `worf` to call the functions below, and the privileges of the sequence's owner, as `ALTER SEQUENCE` does, or of every managed sequence's for `reset_sequence_range()` without one, and `SELECT` to read these views. `enable_snowflake` needs the privileges of `worf.snowflake_node`'s owner.

| Function | Runs on | Does |
| --- | --- | --- |
| `worf.enable_sequence_range(sequence regclass, participants text[] DEFAULT NULL, range_size bigint DEFAULT NULL, max_range_size bigint DEFAULT NULL, pool_start bigint DEFAULT NULL, force boolean DEFAULT false)` | Owner | Puts the sequence under range management. With `participants` `NULL`, it waits for `activate_sequence_range`. `pool_start` raises where the values start |
| `worf.activate_sequence_range(sequence regclass, node_name name DEFAULT NULL)` | Owner, or a pool holder whose fence is up | Starts granting with the nodes that have reported so far, or lifts a fence; with a node named, the fence stops waiting for that node alone |
| `worf.alter_sequence_range(sequence regclass, range_size bigint DEFAULT NULL, max_range_size bigint DEFAULT NULL)` | Owner | Changes the block sizes, each at least 2 |
| `worf.disable_sequence_range(sequence regclass)` | Owner | Stops granting. Each node keeps using the blocks it holds |
| `worf.reset_sequence_range(sequence regclass DEFAULT NULL)` | Any node | Abandons this node's blocks and requests new ones. An owner or pool holder grants nothing until the nodes it granted to report what they hold |
| `worf.reserve_sequence_range(sequence regclass, count bigint, timeout interval DEFAULT '1 minute')` | Any node | Returns once the active block has at least `count` values left, and a twentieth more for other sessions, switching to the next block when that holds them, or to one granted for the load, and once the range worker has reserved the block for the load, the active one too when it holds them. Other sessions draw from it too, so a load that they leave short switches to the next block itself |
| `worf.reserve_sequence_values(sequence regclass, lo bigint, hi bigint, timeout interval DEFAULT '1 minute')` | Any node | Gives this node exactly `[lo, hi]`, for rows that already carry those keys |

A node's first block has `range_size` values: 100 for `smallint`, 10,000 for `integer` and 1,000,000 for `bigint`. A node whose block lasted under an hour asks for twice as many next time, up to `max_range_size`, and one whose block lasted over a day asks for half. A node also asks for at least two minutes of values at its peak insert rate, taken over ten seconds at least, up to `max_range_size`. A switch for `reserve_sequence_range`, and the load in the block it reserves, count toward neither.

## How it works

The owner holds the root, the values not yet granted. Each node draws from its active block and keeps a next block ready. Each database that manages a sequence runs a range worker and an exchange worker, which take two of `max_worker_processes`, and a switch worker for each sequence that transactions hold at its block's end, or in a block it moved back in, or that a load waits for; a database that only subscribes runs the exchange worker briefly to ask its providers whether they manage any, and again `worf.sequence_range_exchange_interval` after it ends; the first time, and when a backend has learned of a sequence, it stays up to one interval longer while a subscription is still making its slot. The range worker switches to the next block when the active one runs low, by setting the sequence's bounds to the block in its catalog row and moving it to the block's start, and asks for another. A switch moves the sequence at once, as `setval` does, and its bounds as the switch commits, so one that rolls back never makes the sequence issue a value again: the next switch to the block goes on from where the sequence got to, and a block the sequence went past after such a rollback is retired unused. Until that switch, the sequence is past its active block, whose bounds it still has, so a statement that would draw from it waits for the switch as at the block's end, or makes it in its transaction. The range worker switches when no transaction that drew from the block holds the sequence, which then waits for the switch's commit. At the block's last twentieth, or for a block reserved for a load, a switch worker switches beside the transactions that hold the sequence, prepared ones too, rather than waiting for them to end, once the statements that hold the sequence's switch gate have let it go, as below. Statements that draw from the sequence, inserts, `MERGE` with an insert and `COPY FROM` into a table whose defaults use it, hold its switch gate, an advisory lock with the sequence's OID and 3 as its `objsubid`, and let it go between their rows while a switch waits for it, so the switch moves the sequence only between their rows, and their next rows take its new bounds. The switch waits for the gate as for a lock, for as long as it takes in a switch worker, so a statement that holds it while it waits for another lock, or that pauses within its rows, as a `COPY FROM STDIN` waiting for its client or a statement in `pg_sleep`, holds the switch up until it goes on, and statements waiting for the switch wait for it at the sequence's door, an advisory lock with 4 as its `objsubid`, as for a lock. A switch worker waits for the gate before it locks the sequence's range row, which exchanges and the range worker take, so such a statement holds up nothing else; an exchange waits for a range row another transaction holds, as one that ran a block out does until it ends, a quarter of `worf.sequence_range_timeout` at most, up to a second, and takes that sequence in at a later exchange. A cycle of such waits, as when a statement holding the gate waits for the key of a transaction that waits for the switch, is a deadlock that PostgreSQL detects, ending one of them with SQLSTATE `40P01`. A statement waits for the switch, or for a next block on its way, rather than run the block out: while the next block is still to come, or once a worker has tried to switch and couldn't, as while a transaction holds the sequence's range row, up to twice `worf.sequence_range_timeout` for each block in all, and while the next block is here and no worker has come to the sequence yet, as on a node too busy to check its sequences in time, until the switch, as for a lock, unless `statement_timeout` or a cancellation ends the wait: before it draws, and after each row, once the block has reached its last twentieth or has no more values left than the statements drawing from it, which may each draw one before they check again, and it checks the next block once it comes. So any number of statements drawing at once go on through the blocks as they arrive. A block reserved for a load is used up before the switch from it, which its load's last row waits for. A transaction that runs the active block out while no other transaction holds the sequence switches it to the next block itself, and holds the sequence until it ends, so other sessions' inserts wait for it; such a transaction can't be prepared. At each block's end after that, it waits for the range worker to bring the next block, which the worker does though it can't check the sequence meanwhile, and switches to it. A `COPY FROM` checks the sequences its table's defaults draw from for each row, as its defaults draw the row's values, rather than once it writes a buffer of rows, so it switches as an insert does. A switch retires what its block has left: the range worker switches once the block has a minute's values left at its peak rate, or a twentieth of it if that is more, but no more than half, and statements wait for the switch from the block's last twentieth. Leave room in `max_worker_processes` for a switch worker for each sequence switched at once. It also leaves the block when it finds the sequence behind where it was at its last check, or behind a value a row holds in the block, in a column that uses the sequence and leads an index, as after a superuser's `setval`, reading the rows again once the sequence has moved or a transaction has ended, at most once a second; a switch worker leaves the block beside the transactions that hold the sequence, as at a block's end, so other inserts wait for it rather than draw those values again. The exchange worker makes the calls to other nodes, over a connection to each that it keeps from one call to the next and makes again after a call fails or runs out of time, so a node that never answers holds up no switch. The worker waits on no node: it looks up the host names libpq would connect to, those a service file or the environment gives too, on other threads, connects to each address they have in turn, with the connection's settings, which go in one round trip, sends each call as the connection's socket takes it, however large, and takes them on as their sockets let it, between its other work and as it waits between rounds, one call at a time with each node, each connection and call having `worf.sequence_range_timeout`. The warnings and errors a node sends over these connections go to this node's log as lines of their own, naming the node, up to ten a minute from each node, with a line that says when more went unlogged; its messages of lower severity, as debug messages, don't. A node whose last call ran out of time, as one whose host drops connection attempts, is probed after a delay, from the end of the call or probe before, that doubles from ten seconds up to a minute, or `worf.sequence_range_exchange_interval` if that is longer, or at once when a statement waits on the node; once a probe's connection is made, the node is called over it at once, and the delay holds until a call is answered. So a node that never answers, or answers slowly, holds up no other node's calls, and one that answers again, though slowly, is reached within about a minute of answering, however many requests the other nodes keep answering. Idle, the workers write only once a neighbor's WAL position has moved by a WAL segment since the tables last recorded it, as checkpoints and other background writes move it, in one transaction, and once an hour on a node that holds a Snowflake node number; otherwise a node uses no transaction IDs, and a neighbor still counts it as live from the exchanges it remembers in shared memory. Nodes reach the owner over their subscriptions: a node asks its neighbor nearest the owner that still exchanges with it, which can't be a neighbor whose own route to the owner goes through the node: a node reports no distance to its parent, and reports its route, the nodes from its parent to the owner, to its other neighbors, which take no route that goes through themselves, so no ring of nodes counts its distances up around itself once the owner is gone; a node with no route keeps its requests until it has one; a node that serves others holds pool blocks to grant from, asking for more before they run out. The owner switches to a block it granted itself only once a neighbor has heard of it, or at once when no neighbor is in touch, so an owner that only answers calls may wait up to an exchange interval for its next block. Each node keeps the reports of up to 1,024 other nodes for a sequence, up to 256 of them that one neighbor relays, which it drops once the neighbor no longer relays them, and notes in memory up to 256 that one neighbor relays. No node can check the reports a neighbor relays for others, so a subscriber's role can make up reports of other nodes, up to those limits, as well as its own. At worst they hold the sequence up, by keeping its root from starting, a fence from lifting or a Snowflake node number from coming back, make a node give up its Snowflake node number, or make the root of a later epoch start above a made-up watermark. An owner takes a watermark a neighbor reports only up to two of its largest blocks beyond its own blocks and the last grant its ledger holds of other nodes', with a warning, so that a fence a made-up watermark brings on gives up no more of the root's values than that as it lifts. Once it has taken a watermark beyond its own, the blocks it grants itself beyond that one count toward the bound only as far as it draws from them, but each block it grants another node, the reporting role's own included, moves the bound past that block, so a role that keeps asking for blocks and making up watermarks makes each fence give up up to two of the largest blocks more. A made-up request to reset, which a node sends a neighbor whose WAL position it sees move back, or a made-up watermark beyond the owner's, makes the node give up its blocks, and fence its root if it is the owner, at once the first time, then no more than once in the ten minutes after for each neighbor, and twice as long after each reset that comes within a day of the end of the last such window, up to a day, and half as long, down to ten minutes, for each two days and a window more in which the neighbor could have and didn't, so that a neighbor that pauses its requests gets no more resets than one that keeps asking, with the resets of the minute after, which one rollback brings for every sequence, each sequence once; the neighbor keeps asking meanwhile, and takes no grant from the node and answers none of its requests while it sees the node's WAL position behind where it was. A server keeps the limit in memory, so it takes the first request after it starts, as after a restore, at once. A node that `worf.activate_sequence_range` stopped waiting for, as gone, is asked to reset once it's heard from again after the fence lifted, whatever it reports, which may have given out its values again, whether or not it has drawn since it last reset, and so is every holder of grants that overlap, on every forced lift. Such a node draws none of those values meanwhile: after its server starts, a node draws from a block another node granted it, its parent or one that was, only once a message of that node's, made after it heard of the start and asked every reset it owes the node, has come and committed with each reset it asks taken in, as that node's answer to the node's first exchange after it starts is, and a pool holder grants its children nothing from a pool block until the node that granted it has answered so. Until then, what would draw from such a block waits: a call of `nextval` of the sequence that the expressions starting around it name, by the sequence or by its name as text, in any schema, as a function or through an operator: a statement's plan, with the CHECK constraints of the domains it coerces to or a function's column definition list names, as each row of a multi-row `VALUES` list starts as it's read, or, within it, a PL/pgSQL expression, which PL/pgSQL starts outside a plan, as a trigger's or a function's that partition pruning calls as the plan starts; the CHECK constraints and trigger conditions of the tables a statement, a `COPY FROM` or a worf worker's row writes, and their partitions', which start with the first row each takes; the defaults, `WHERE` condition and column domains' CHECK constraints a `COPY FROM` starts; the defaults and CHECK constraints `ALTER TABLE` starts, the CHECK `ALTER DOMAIN` checks, an `EXECUTE`'s parameters and a `CALL`'s arguments; the `RETURNING` list, `WITH CHECK OPTION`, `ON CONFLICT` expressions and `MERGE` actions a statement starts for each partition it routes rows to; and the defaults of the columns a worf worker's row, or a table it copies, doesn't carry. The CHECK constraints, defaults and conditions count with the bodies of the SQL functions they call that the planner inlines as they start. So does an insert into a table whose default or identity column draws from it, as a partition's identity column drawing from its parent's sequence does from PostgreSQL 17 on, where PostgreSQL marks the partition's column an identity column, as it does for a partition it creates or attaches, in the same session too, though not for a partition of a table it attaches, an `UPDATE` or a `MERGE` that sets such a column to its default, and a statement a worf worker applies, as DDL `replicate_ddl_command` queued, whose failure the worker applies again later under any `worf.exception_behaviour`. A call whose sequence those don't name, as one computed as it runs, one an `ALTER TABLE` that changes a column's type starts, or one code worf doesn't see into starts, as a C function's, waits for every node the server hasn't heard from so, whatever sequence it draws from, even one no range manages, as worf can't tell which sequence that is before it runs. C code starts such a call as it checks a value against a domain whose CHECK draws, as a function that tests an input against a type it names as text does, as `pg_input_is_valid` does, and that call can come where a call the expressions name was counted, which starts later or never, so while a statement calls such a function, or one in a language other than SQL and PL/pgSQL, as a trigger of a table it writes may be, every call the expressions name waits for the nodes that granted the blocks of the sequences any domain's CHECK in the database names too, or for every node when one of them names none. Each has that exchange made at once, and again half `worf.sequence_range_timeout` after each that fails, and waits up to twice `worf.sequence_range_timeout`, after which it fails naming the node, and the sequence when its statement names it, as one that `statement_timeout` ends first does too; so while the node is down, or a prepared transaction holds the sequence's range row, which leaves the sequence out of exchanges, nothing draws from the blocks it granted. Nothing else waits: `nextval` of a sequence no range manages, or of a temporary one, that those name, an `UPDATE` or a `MERGE` that sets a column to a value rather than its default, reads of the sequence, `setval`, `currval`, `EXPLAIN`, though a function or a domain's CHECK its partition pruning runs as the plan starts waits as above, for the sequences those name, worf's own statements, a read-only transaction, a standby, and Snowflake IDs, which carry their times. A statement on a node with no block to draw from, as one that just reset, waits for the block its range worker asks for, up to twice `worf.sequence_range_timeout`. A forced lift's request to reset from the node's grantor that names a block the node holds from the grantor, which the reset gives up, has a limit of its own, so that another request's reset doesn't hold it up, which starts at ten seconds rather than ten minutes, as one forced lift may come soon after another, and grows as above: the grantor's lifts may reset the node 9 times in their first hour and 14 in their first day, beside the 3 and 8 of its other requests, and then once a day each, made-up ones too, which may name the blocks the node's answers list; a lift that names none waits for the other limit. Before its root starts, as when the owner moved and collects what the old blocks reached, it takes a watermark as reported, since it can't know what the old owner granted, so one made-up report can make the root start at its end. The owner logs a warning once the root has granted nine tenths of its values.

Two triggers on each table that uses the sequence check every row a local session writes, after any `BEFORE` trigger has changed it: a new row's value, and a value an update changes. worf creates them as the table's owner, and fires no event trigger for them. The update's trigger fires only on an update that sets the column, unless a row trigger that runs before an update, on the table or any table of its partition tree, or before an insert into a partition, which an update that moves a row there runs, could change it. A value passes when it is in one of this node's blocks and the sequence has passed it. Any other value fails the statement with SQLSTATE `23514`. Apply and sync workers write other nodes' rows unchecked, and the DDL they apply checks rows as a restore does, below. A partitioned table's triggers check every partition, in the columns the table numbers from the sequence. A partition whose own default numbers another column from it, or that of a partitioned table between, has triggers of its own for that column, so attaching it holds up no writers to the rest of the tree. An `UPDATE`, or a `MERGE` without an `INSERT` action, that moves a row to another partition is checked as an update, so the row keeps its value, except in a partition's own column, which checks the moved row as a new one, as a `MERGE` with an `INSERT` action does. The column must be `smallint`, `integer`, `bigint` or `numeric`, in a table or a partitioned table, and its default, or its domain's when it has none of its own, `nextval` of the sequence, alone or cast to the column's type; worf refuses any other default that uses it, such as `nextval('s') + 1000000`, whose values would always fail. A default that only reads the sequence, as `currval` does, leaves its column alone. worf finds the columns that use a sequence by the dependencies PostgreSQL records, and by the name a default gives it as text, as `nextval('s'::text)` or `nextval('s' || '_seq')` does: a default that names the sequence with its schema guards its column, and so does one that names it without, when the sequence is in the table's schema, or the table's schema has nothing of that name, whatever search path the session that sets the default, or alters the table later, has. A column's values are checked under the sequence the name finds as each row is written, if that one is managed, and otherwise under the one it stands for. worf refuses a default that calls `nextval` of a name it can't tell, as one a function returns, once a sequence is managed, and enabling a sequence while such a default exists. A default that calls a function which calls `nextval` leaves its table unguarded.

DDL that brings rows under the triggers, by setting a column's default to the sequence, attaching a partition to a guarded table, `ALTER SEQUENCE ... OWNED BY` or a column's type change, fails with SQLSTATE `23514` if a row holds a value the triggers would refuse, other than one from before range management started or a `numeric` value that isn't a whole `bigint`. A btree index that the column leads, without a predicate, or a validated `CHECK` constraint on the column that rules out the values it looks for, or a partition's bound on it under a partition key of plain columns, spares the check from reading every row; otherwise it reads them all. It reads them with PostgreSQL's own scans, whatever the table's row-level security, so it runs none of the table's functions and needs no rights on the table or its schema.

To restore rows that other nodes wrote, or that predate range management, as `pg_restore` of a table does, set `worf.sequence_range_restore`, which needs a superuser or `GRANT SET ON PARAMETER`. The triggers and the DDL then refuse only the values a sequence may still issue as far as this node knows: ahead of this node's sequence in its blocks, not yet granted to any node, or past every grant. A node can't tell the values another node has issued from those it has yet to issue, so a restored row may hold a key that node issues again.

A transaction that needs more values than the active block has left switches to the next block itself, as above, and fails at the block's end when no next block is ready, or another transaction holds the sequence there too. Before a large load, reserve enough values, before the load's transaction calls `nextval` on the sequence. Other sessions go on drawing from the block, and a load they leave short goes on in the next block:

```sql
BEGIN;
SELECT worf.reserve_sequence_range('inventory_id_seq', 500000);
-- the load
COMMIT;
```

To load rows that already carry keys, or bring them under the triggers, reserve exactly those keys on the node that loads them. The owner refuses keys that may already be in use. Both reservations need the privileges of the sequence's owner.

A transaction that has called `nextval`, or written a value the guard checked against the active block, and stays open, prepared or not, holds off the range worker's own switch to the next block until it ends; from the block's last twentieth, a switch worker switches beside it instead, and so beside a statement that holds the switch gate while it waits for another lock, as an insert waiting for a key another transaction wrote.

## Moving the owner

Run `disable_sequence_range` on the old owner, then `enable_sequence_range` on the new one, naming every participant. The new owner's values start above every block the old owner granted, and nodes keep using their blocks until new ones arrive. If the old owner is gone for good, pass `force := true`.

Dropping a managed sequence, or the table that owns it, ends its range management on that node, and the range worker removes its range state once the drop commits, so the drop never waits on the rows worf's workers hold. On the owner, the other nodes hear that it is disabled and keep using the blocks they hold. A sequence of the same name, as `pg_restore` brings back, isn't managed there until `enable_sequence_range` starts a new epoch above the dropped one's values. On another node, one joins the owner's epoch again as it is created, as when its table is dropped and created again, and issues no values until its blocks arrive. Should the epoch turn out to be disabled, as when the word of it arrived only after, the sequence stays parked, since other nodes' blocks may hold its values, until the owner enables it again for a new epoch, naming the node.

## Restores and failover

A node whose node id, system identifier or timeline changes, as after a promotion, `pg_upgrade` or point-in-time recovery, abandons its blocks and asks for new ones. An owner or pool holder also fences its root and pool blocks: it grants nothing until every node it exchanges with, each that called it through one of its slots and each provider it subscribes to, even one that is down or whose exchanges carried no managed sequence, reports the blocks it holds, or that it doesn't manage the sequence, or `activate_sequence_range` lifts the fence. Only a node's own report counts, never one a neighbor relays, and `worf.sequence_ranges` names the nodes the fence waits for. A node stops counting for later fences once the subscriptions between them are dropped, a subscriber telling its provider as it drops its own, once another node takes over its slot, or once its rows in `worf.sequence_range_link` are deleted, as `drop_subscription` asks when it can't reach the provider, which is safe only while no fence is up. A fence that is up keeps waiting for every node it waited for as it went up, whatever happens to their links or subscriptions, since a node restored from a backup may have granted one of them blocks that only its report brings back: until that node reports, subscribing again if it must, or `activate_sequence_range` naming that node, as `worf.sequence_ranges` does, stops the wait for it, as for a node gone for good, which reissues any values the node holds that the owner lost. Without a node named, `activate_sequence_range` stops waiting for every node, so it is safe only when the fence waits for no node that may still report. `activate_sequence_range` also lifts a fence that grants overlapping each other hold, with a warning: every holder of a grant that overlaps another resets, the others as they hear from this node, so values they shared that any of them issued before then may have been issued twice. A node's slots don't count, since a restore from a backup has none. It takes back into its ledger any grant it lost. The owner then also gives up its free values up to the highest value any node has seen granted.

A restore from a backup or a snapshot keeps the timeline. The node's neighbors notice its WAL position moving backwards, behind where it was at an exchange or behind its changes they applied, or its granting values they already hold, and tell it to reset, which does the same as a change of identity. Until it has, they take no grant from it and answer none of its requests. An owner or pool holder also resets on its own once a neighbor holds a block it granted and has no record of, and an owner once a neighbor has heard of grants beyond the last it knows of. They notice only at their next exchange, and not at all once the node has written past where they saw its WAL position or applied its changes to, so a restored node may issue values it issued before. Keep writes away from a restored node until `reset_sequence_range` has run on it.

A node that `worf_create_subscriber` makes from a base backup gives up its source's blocks and stops its managed sequences before it takes a node id of its own. The rows it copied reach into the root, so it is refused until the sequence moves to a new epoch: run `disable_sequence_range` and then `enable_sequence_range` on the owner, naming the new node among the participants.

An owner or pool holder that loses grants without its neighbors noticing, as when it is restored to before its first exchange with a node, which it then doesn't wait for, or loses a grant in a crash, may grant those values again. A synchronous standby for each of them prevents a crash from losing a grant.

## Snowflake IDs

Where the schema can change, a `bigint` column can take Snowflake IDs instead, which need no blocks:

```sql
-- On one node, naming the others
SELECT worf.enable_snowflake(participants := '{node_beta}');

CREATE TABLE events (id bigint PRIMARY KEY DEFAULT worf.snowflake_id(), payload jsonb);
```

An ID holds the milliseconds since 2025 in its top 41 bits, the node's number in the next 10 and a counter in the last 12, so up to 1,024 nodes at a time each issue up to 4,096 IDs a millisecond, and the IDs sort by time. Node numbers come from the same allocator as sequence ranges, so no number is held by two nodes, and `worf.snowflake_node()` shows this node's. A node that changes identity takes a new number; `reset_sequence_range()` without a sequence keeps it. Moving the owner of the numbers never runs out of them: once the owner has none left to grant, a number comes back once its holder has reported to the owner itself, a day after the grant, without it, or has reported nothing for a day, and every other node has done the same, while the numbers of a pool block a node holds to grant on stay its as long as it reports, and it grants none of them once it hasn't heard from the owner for 12 hours; its new holder's IDs start after every time its earlier holders reserved, up to a day ahead of the owner's clock. Reports a neighbor relays never bring a number back. A node that hasn't heard from the owner of the numbers, directly or through its neighbors, for 12 hours gives up its number, since the owner may give it to another node, and takes a new one once it hears from the owner again. It records hearing from the owner at least once an hour, so that it keeps its number across a restart. A node that sees another report holding its number gives it up too. Each node's IDs only grow, even when its clock goes back across a restart, since the node records how far ahead the clock may run before it issues IDs that far.

## Restrictions

Managed sequences can't cycle, be temporary or unlogged, or be in a replication set; `replication_set_add_all_sequences` leaves them out. Except when worf runs it, worf rejects:

- `ALTER SEQUENCE` on them, other than `OWNED BY` and `OWNER TO`, including `RENAME`, `SET SCHEMA` and `SET UNLOGGED`;
- renaming their schema, and moving or unlogging a table that owns one;
- `GRANT UPDATE` or `GRANT ALL` on them, directly or through `ALL SEQUENCES IN SCHEMA`;
- changing the default or identity of a column that uses one, other than giving a column the sequence owns a default of `nextval` of it, and the default of a domain that uses one;
- dropping, renaming or disabling the guard triggers and making them depend on an extension, and, wherever worf is installed, creating other triggers with their names or function or renaming a trigger to or from them;
- `TRUNCATE ... RESTART IDENTITY` that would restart one, including through `CASCADE` or inheritance without `ONLY`.
- `PREPARE TRANSACTION` for a transaction that switched one itself, that ran `enable_sequence_range`, `alter_sequence_range`, `disable_sequence_range`, `activate_sequence_range`, `reset_sequence_range`, `reserve_sequence_range` or `reserve_sequence_values`, or that changed the type of an identity column a managed sequence numbers, unless a savepoint rolled it back: a prepared transaction would hold the sequence, or its range row, across restarts, and the sequence could neither switch nor exchange blocks until it ended. A prepared transaction that holds the range row anyway, as a superuser's that locks it, holds up only that sequence's exchanges, which leave it out until the transaction ends: its row in `worf.sequence_ranges` names the transaction, and the log warns once.

A `CREATE TRIGGER` of the guard, as a restored dump holds, is skipped, since worf creates the triggers on the tables that need them, and replaces any triggers with their names that predate it. A column that uses a managed sequence can change its type, an identity column's sequence with it as long as the new type holds the blocks the node draws from, or be dropped, and worf puts the triggers back for the columns that still use one. A type change with `USING`, or from `numeric`, checks the column's rows again.

Superusers and members of `pg_write_all_data` can still call `setval`. The range worker leaves the block only when it finds the sequence behind where it was at its last check or behind a row, as above, so a `setval` back to a value past both makes the sequence issue again the values it issued beyond it that no row in an indexed column holds.
