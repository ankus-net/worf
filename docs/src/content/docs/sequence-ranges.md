---
title: Sequence ranges
description: Give each node blocks of a sequence's values, so rows inserted on different nodes never share a key.
---

Nodes that all insert into the same table need keys that never collide. Sequence ranges give each node blocks of a sequence's values that no other node uses, with no change to the tables or the sequence's type. `nextval` and column defaults keep working as before.

## Enabling

On the node that will own the sequence's values, name every other node that issues values from it:

```sql
SELECT worf.enable_sequence_range('inventory_id_seq', participants := '{node_beta}');
```

The other nodes learn of the sequence over their subscriptions, so each node needs a subscription to or from another node in the topology. The user in each provider connection string needs `EXECUTE` on `worf.sequence_range_exchange`, which `PUBLIC` doesn't have. A provider tells the nodes that call it apart by these users alone, so give each subscriber node its own: a user that isn't a superuser speaks for the first node it calls for, and no other, until its row in `worf.sequence_range_role` is deleted. A node re-created under a new name, with the same subscription name and user, takes over its old node's slot then, or, for a superuser, once the old node has been silent for three exchange intervals and a timeout. Once every participant has reported, the owner starts granting blocks above every value any node has issued or stored. Until a node gets its first block, and whenever it has none, as while a reset owner is fenced, its `nextval` fails with SQLSTATE `2200H`, "reached maximum value" (or minimum, for a descending sequence) at the edge of the sequence's type where worf parks it, such as -9223372036854775807; `worf.sequence_ranges` shows why. A node that joins later, with values that already reach into the granted range, is refused: its state shows `refused` and its `nextval` keeps failing.

```sql
SELECT * FROM worf.sequence_ranges;
```

shows each sequence's state, its active and next blocks, and the values left. `worf.sequence_range_grants` lists the blocks this node granted. A role that isn't a superuser needs `USAGE` on schema `worf` to call the functions below, and the privileges of the sequence's owner, as `ALTER SEQUENCE` does, or of every managed sequence's for `reset_sequence_range()` without one, and `SELECT` to read these views. `enable_snowflake` needs the privileges of `worf.snowflake_node`'s owner.

| Function | Runs on | Does |
| --- | --- | --- |
| `worf.enable_sequence_range(sequence regclass, participants text[] DEFAULT NULL, range_size bigint DEFAULT NULL, max_range_size bigint DEFAULT NULL, pool_start bigint DEFAULT NULL, force boolean DEFAULT false)` | Owner | Puts the sequence under range management. With `participants` `NULL`, it waits for `activate_sequence_range`. `pool_start` raises where the values start |
| `worf.activate_sequence_range(sequence regclass, node_name name DEFAULT NULL)` | Owner, or a pool holder whose fence is up | Starts granting with the nodes that have reported so far, or lifts a fence; with a node named, the fence stops waiting for that node alone |
| `worf.alter_sequence_range(sequence regclass, range_size bigint DEFAULT NULL, max_range_size bigint DEFAULT NULL)` | Owner | Changes the block sizes, each at least 2 |
| `worf.disable_sequence_range(sequence regclass)` | Owner | Stops granting. Each node keeps using the blocks it holds |
| `worf.reset_sequence_range(sequence regclass DEFAULT NULL)` | Any node | Abandons this node's blocks and requests new ones. An owner or pool holder grants nothing until the nodes it granted to report what they hold |
| `worf.reserve_sequence_range(sequence regclass, count bigint, timeout interval DEFAULT '1 minute')` | Any node | Returns once the active block has at least `count` values left, and a twentieth more for other sessions, switching to the next block when that holds them, or to one granted for the load. Other sessions draw from it too, so a load that they leave short switches to the next block itself |
| `worf.reserve_sequence_values(sequence regclass, lo bigint, hi bigint, timeout interval DEFAULT '1 minute')` | Any node | Gives this node exactly `[lo, hi]`, for rows that already carry those keys |

A node's first block has `range_size` values: 100 for `smallint`, 10,000 for `integer` and 1,000,000 for `bigint`. A node whose block lasted under an hour asks for twice as many next time, up to `max_range_size`, and one whose block lasted over a day asks for half. A node also asks for at least two minutes of values at its peak insert rate, taken over ten seconds at least, up to `max_range_size`. A switch for `reserve_sequence_range`, and the load in the block it switches to, count toward neither.

## How it works

The owner holds the root, the values not yet granted. Each node draws from its active block and keeps a next block ready. Each database that manages a sequence runs a range worker and an exchange worker, which take two of `max_worker_processes`, and a switch worker for each sequence that transactions hold at its block's end, or that a load waits for; a database that only subscribes runs the exchange worker briefly to ask its providers whether they manage any, and again `worf.sequence_range_exchange_interval` after it ends; the first time, and when a backend has learned of a sequence, it stays up to one interval longer while a subscription is still making its slot. The range worker switches to the next block when the active one runs low, by setting the sequence's `MINVALUE` and `MAXVALUE` to the block, and asks for another. An insert that reaches the last twentieth of the active block waits, up to twice `worf.sequence_range_timeout` for each block in all, for the worker to start the switch, or for a next block on its way, rather than run the block out. The range worker waits a tenth of a second at most for the transactions that drew from the block, so inserts queue behind a switch no longer than that. At the block's last twentieth, or for a block reserved for a load, a switch worker waits for those transactions however long they hold the sequence, while the range worker goes on with the other sequences, and inserts into the sequence wait behind it rather than run the block out, so a transaction that holds the sequence there holds up its inserts until it ends. A prepared transaction, which may hold the sequence across restarts, isn't waited for: `worf.sequence_ranges` names it, sessions that insert get a warning, and the inserts run the block out. Nor is any transaction waited for while every worker slot is taken, though the range worker's own wait still switches the block under short transactions, so leave room in `max_worker_processes` for a switch worker for each sequence held at once. A transaction that runs the active block out itself, as one whose rows need more values than the block has left, switches the sequence to the next block in the transaction: it waits for the other transactions that hold the sequence, up to `worf.sequence_range_timeout`, and holds the sequence until it ends, so other sessions' inserts wait for it. A `COPY FROM` does so before it starts, and as its rows reach the block's last thousand values, since it draws a thousand values before the guard sees them. Two transactions that both hold the sequence at the block's end can't both switch it, so one of them fails there, and so does a transaction while a prepared transaction holds the sequence. It also leaves the block when it finds the sequence behind where it was at its last check, or behind a value a row holds in the block, in a column that uses the sequence and leads an index, as after a superuser's `setval`. The exchange worker makes the calls to other nodes, so a node that never answers holds up no switch, and the range worker cancels a call after `worf.sequence_range_timeout`. The worker calls one node at a time, a node whose last call ran out of time after the others, and calls that node again after a delay that doubles up to a minute, or `worf.sequence_range_exchange_interval` if that is longer. Idle, the workers write only once a neighbor's WAL position has moved by a WAL segment since the tables last recorded it, as checkpoints and other background writes move it, in one transaction, and once an hour on a node that holds a Snowflake node number; otherwise a node uses no transaction IDs, and a neighbor still counts it as live from the exchanges it remembers in shared memory. Nodes reach the owner over their subscriptions: a node asks its neighbor nearest the owner that still exchanges with it, and a node that serves others holds pool blocks to grant from, asking for more before they run out. The owner switches to a block it granted itself only once a neighbor has heard of it, or at once when no neighbor is in touch, so an owner that only answers calls may wait up to an exchange interval for its next block. Each node keeps the reports of up to 1,024 other nodes for a sequence, up to 256 of them that one neighbor relays, which it drops once the neighbor no longer relays them, and notes in memory up to 256 that one neighbor relays. No node can check the reports a neighbor relays for others, so a subscriber's role can make up reports of other nodes, up to those limits, as well as its own. At worst they hold the sequence up, by keeping its root from starting, a fence from lifting or a Snowflake node number from coming back, make a node give up its Snowflake node number, or make the root of a later epoch start above a made-up watermark. An owner takes a watermark a neighbor reports only up to two of its largest blocks beyond its own blocks and the last grant its ledger holds of other nodes', with a warning, so that a fence a made-up watermark brings on gives up no more of the root's values than that as it lifts. Once it has taken a watermark beyond its own, the blocks it grants itself beyond that one count toward the bound only as far as it draws from them, but each block it grants another node, the reporting role's own included, moves the bound past that block, so a role that keeps asking for blocks and making up watermarks makes each fence give up up to two of the largest blocks more. A made-up request to reset, which a node sends a neighbor whose WAL position it sees move back, makes that neighbor give up its blocks, and fence its root if it is the owner, but no more than once every ten minutes for each neighbor, and a made-up watermark resets an owner no more often. Before its root starts, as when the owner moved and collects what the old blocks reached, it takes a watermark as reported, since it can't know what the old owner granted, so one made-up report can make the root start at its end. The owner logs a warning once the root has granted nine tenths of its values.

Two triggers on each table that uses the sequence check every row a local session writes, after any `BEFORE` trigger has changed it: a new row's value, and a value an update changes. worf creates them as the table's owner, and fires no event trigger for them. The update's trigger fires only on an update that sets the column, unless a row trigger that runs before an update, on the table or any table of its partition tree, or before an insert into a partition, which an update that moves a row there runs, could change it. A value passes when it is in one of this node's blocks and the sequence has passed it. Any other value fails the statement with SQLSTATE `23514`. Apply and sync workers write other nodes' rows unchecked, and the DDL they apply checks rows as a restore does, below. A partitioned table's triggers check every partition, in the columns the table numbers from the sequence. A partition whose own default numbers another column from it, or that of a partitioned table between, has triggers of its own for that column, so attaching it holds up no writers to the rest of the tree. An `UPDATE`, or a `MERGE` without an `INSERT` action, that moves a row to another partition is checked as an update, so the row keeps its value, except in a partition's own column, which checks the moved row as a new one, as a `MERGE` with an `INSERT` action does. The column must be `smallint`, `integer`, `bigint` or `numeric`, in a table or a partitioned table, and its default, or its domain's when it has none of its own, `nextval` of the sequence, alone or cast to the column's type; worf refuses any other default that uses it, such as `nextval('s') + 1000000`, whose values would always fail. A default that only reads the sequence, as `currval` does, leaves its column alone. worf finds the columns that use a sequence by the dependencies PostgreSQL records, and by the name a default gives it as text, as `nextval('s'::text)` or `nextval('s' || '_seq')` does: a default that names the sequence with its schema guards its column, and so does one that names it without, when the sequence is in the table's schema, or the table's schema has nothing of that name, whatever search path the session that sets the default, or alters the table later, has. A column's values are checked under the sequence the name finds as each row is written, if that one is managed, and otherwise under the one it stands for. worf refuses a default that calls `nextval` of a name it can't tell, as one a function returns, once a sequence is managed, and enabling a sequence while such a default exists. A default that calls a function which calls `nextval` leaves its table unguarded.

DDL that brings rows under the triggers, by setting a column's default to the sequence, attaching a partition to a guarded table, `ALTER SEQUENCE ... OWNED BY` or a column's type change, fails with SQLSTATE `23514` if a row holds a value the triggers would refuse, other than one from before range management started or a `numeric` value that isn't a whole `bigint`. A btree index that the column leads, without a predicate, or a validated `CHECK` constraint on the column that rules out the values it looks for, or a partition's bound on it under a partition key of plain columns, spares the check from reading every row; otherwise it reads them all. It reads them with PostgreSQL's own scans, whatever the table's row-level security, so it runs none of the table's functions and needs no rights on the table or its schema.

To restore rows that other nodes wrote, or that predate range management, as `pg_restore` of a table does, set `worf.sequence_range_restore`, which needs a superuser or `GRANT SET ON PARAMETER`. The triggers and the DDL then refuse only the values a sequence may still issue as far as this node knows: ahead of this node's sequence in its blocks, not yet granted to any node, or past every grant. A node can't tell the values another node has issued from those it has yet to issue, so a restored row may hold a key that node issues again.

A transaction that needs more values than the active block has left switches to the next block itself, as above, and fails at the block's end when no next block is ready, or another transaction holds the sequence there too. Before a large load, reserve enough values, before the load's transaction calls `nextval` on the sequence. Other sessions go on drawing from the block, and a load they leave short goes on in the next block:

```sql
BEGIN;
SELECT worf.reserve_sequence_range('inventory_id_seq', 500000);
-- the load
COMMIT;
```

To load rows that already carry keys, or bring them under the triggers, reserve exactly those keys on the node that loads them. The owner refuses keys that may already be in use. Both reservations need the privileges of the sequence's owner.

A transaction that has called `nextval`, or written a value the guard checked against the active block, and stays open holds off the switch to the next block until it ends.

## Moving the owner

Run `disable_sequence_range` on the old owner, then `enable_sequence_range` on the new one, naming every participant. The new owner's values start above every block the old owner granted, and nodes keep using their blocks until new ones arrive. If the old owner is gone for good, pass `force := true`.

Dropping a managed sequence, or the table that owns it, ends its range management on that node, and the range worker removes its range state once the drop commits, so the drop never waits on the rows worf's workers hold. On the owner, the other nodes hear that it is disabled and keep using the blocks they hold. A sequence of the same name, as `pg_restore` brings back, isn't managed there until `enable_sequence_range` starts a new epoch above the dropped one's values. On another node, one joins the owner's epoch again as it is created, as when its table is dropped and created again, and issues no values until its blocks arrive. Should the epoch turn out to be disabled, as when the word of it arrived only after, the sequence stays parked, since other nodes' blocks may hold its values, until the owner enables it again for a new epoch, naming the node.

## Restores and failover

A node whose node id, system identifier or timeline changes, as after a promotion, `pg_upgrade` or point-in-time recovery, abandons its blocks and asks for new ones. An owner or pool holder also fences its root and pool blocks: it grants nothing until every node it exchanges with, each that called it through one of its slots and each provider it subscribes to, even one that is down or whose exchanges carried no managed sequence, reports the blocks it holds, or that it doesn't manage the sequence, or `activate_sequence_range` lifts the fence. Only a node's own report counts, never one a neighbor relays, and `worf.sequence_ranges` names the nodes the fence waits for. A node stops counting for later fences once the subscriptions between them are dropped, a subscriber telling its provider as it drops its own, once another node takes over its slot, or once its rows in `worf.sequence_range_link` are deleted, as `drop_subscription` asks when it can't reach the provider, which is safe only while no fence is up. A fence that is up keeps waiting for every node it waited for as it went up, whatever happens to their links or subscriptions, since a node restored from a backup may have granted one of them blocks that only its report brings back: until that node reports, subscribing again if it must, or `activate_sequence_range` naming that node, as `worf.sequence_ranges` does, stops the wait for it, as for a node gone for good, which reissues any values the node holds that the owner lost. Without a node named, `activate_sequence_range` stops waiting for every node, so it is safe only when the fence waits for no node that may still report. `activate_sequence_range` also lifts a fence that grants overlapping each other hold, with a warning: both holders reset, the other as it hears from this node, so values they shared that either issued before then may have been issued twice. A node's slots don't count, since a restore from a backup has none. It takes back into its ledger any grant it lost. The owner then also gives up its free values up to the highest value any node has seen granted.

A restore from a backup or a snapshot keeps the timeline. The node's neighbors notice its WAL position moving backwards, behind where it was at an exchange or behind its changes they applied, or its granting values they already hold, and tell it to reset, which does the same as a change of identity. Until it has, they take no grant from it and answer none of its requests. An owner or pool holder also resets on its own once a neighbor holds a block it granted and has no record of, and an owner once a neighbor has heard of grants beyond the last it knows of. They notice only at their next exchange, and not at all once the node has written past where they saw its WAL position or applied its changes to, so a restored node may issue values it issued before. Keep writes away from a restored node until `reset_sequence_range` has run on it.

A node that `worf_create_subscriber` makes from a base backup gives up its source's blocks and stops its managed sequences before it takes a node id of its own. The rows it copied reach into the root, so it is refused until the sequence moves to a new epoch: run `disable_sequence_range` and then `enable_sequence_range` on the owner, naming the new node among the participants.

An owner or pool holder that loses grants without its neighbors noticing, as when it is restored to before its first exchange with a node, which it then doesn't wait for, or loses a grant in a crash, may grant those values again. A synchronous standby for each of them prevents a crash from losing a grant.

## Snowflake IDs

Where the schema can change, a `bigint` column can take Snowflake IDs instead, which need no blocks:

```sql
-- On one node, naming the others
SELECT worf.enable_snowflake(participants := '{node_beta}');

CREATE TABLE events (id bigint PRIMARY KEY DEFAULT worf.snowflake_id(), payload jsonb);
```

An ID holds the milliseconds since 2025 in its top 41 bits, the node's number in the next 10 and a counter in the last 12, so up to 1,024 nodes at a time each issue up to 4,096 IDs a millisecond, and the IDs sort by time. Node numbers come from the same allocator as sequence ranges, so no number is held by two nodes, and `worf.snowflake_node()` shows this node's. A node that changes identity takes a new number; `reset_sequence_range()` without a sequence keeps it. Moving the owner of the numbers never runs out of them: once the owner has none left to grant, a number comes back once its holder has reported to the owner itself, a day after the grant, without it, or has reported nothing for a day, and every other node has done the same, while the numbers of a pool block a node holds to grant on stay its as long as it reports, and it grants none of them once it hasn't heard from the owner for 12 hours; its new holder's IDs start after every time its earlier holders reserved, up to a day ahead of the owner's clock. Reports a neighbor relays never bring a number back. A node that hasn't heard from the owner of the numbers, directly or through its neighbors, for 12 hours gives up its number, since the owner may give it to another node, and takes a new one once it hears from the owner again. It records hearing from the owner at least once an hour, so that it keeps its number across a restart. A node that sees another report holding its number gives it up too. Each node's IDs only grow, even when its clock goes back across a restart, since the node records how far ahead the clock may run before it issues IDs that far.

## Restrictions

Managed sequences can't cycle, be temporary or unlogged, or be in a replication set; `replication_set_add_all_sequences` leaves them out. Except when worf runs it, worf rejects:

- `ALTER SEQUENCE` on them, other than `OWNED BY` and `OWNER TO`, including `RENAME`, `SET SCHEMA` and `SET UNLOGGED`;
- renaming their schema, and moving or unlogging a table that owns one;
- `GRANT UPDATE` or `GRANT ALL` on them, directly or through `ALL SEQUENCES IN SCHEMA`;
- changing the default or identity of a column that uses one, other than giving a column the sequence owns a default of `nextval` of it, and the default of a domain that uses one;
- dropping, renaming or disabling the guard triggers and making them depend on an extension, and, wherever worf is installed, creating other triggers with their names or function or renaming a trigger to or from them;
- `TRUNCATE ... RESTART IDENTITY` that would restart one, including through `CASCADE` or inheritance without `ONLY`.

A `CREATE TRIGGER` of the guard, as a restored dump holds, is skipped, since worf creates the triggers on the tables that need them, and replaces any triggers with their names that predate it. A column that uses a managed sequence can change its type, an identity column's sequence with it as long as the new type holds the blocks the node draws from, or be dropped, and worf puts the triggers back for the columns that still use one. A type change with `USING`, or from `numeric`, checks the column's rows again.

Superusers and members of `pg_write_all_data` can still call `setval`. The range worker leaves the block only when it finds the sequence behind where it was at its last check or behind a row, as above, so a `setval` back to a value past both makes the sequence issue again the values it issued beyond it that no row in an indexed column holds.
